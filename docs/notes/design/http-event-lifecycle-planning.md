## Proposed pure and effect boundaries

Use portable `.cljc` shapes/laws for lifecycle modes, owned state, requested command, admissibility, operation identity/generation and typed outcome. Prefer a small explicit decision function over a second global mutable lifecycle authority. Proposed states distinguish stopped, starting, running, stopping and failed/partial cleanup, with disabled represented as admission information rather than a false running state. Exact vocabulary, arities and ABI are reviewed decisions; this document does not establish a public API.

Infra owns instance-scoped handles and executes the decided sequence. Named extern adapters own raw JS promises, timers, Fastify, process signals, SDK objects and filesystems; pure/domain layers see Clojure maps/scalars and opaque owned handles only at supported boundaries. The coordinator resolves async completion before accepting success, retains the primary failure and all cleanup failures, and validates result shape. Status reports the observed owned runtime, not desired mode or a premature Boolean. Do not widen backend TypeScript, relocate effects into domain, introduce Clio/Rheos authority or patch the separately owned generator runtime.

The outer trusted composition binds an immutable lifecycle context/capability set. Resource/generator/HTTP inputs can request operations but cannot replace or create trusted capabilities. Retain separately owned #161 source/trigger/schedule provenance, internal/external distinctions and Discord closure compatibility through any proposed config/start/reload/tools-route changes. Merge only after fresh overlap/qualification guards; a plan reference is not dependency admission.

## HTTP-only and full composition

HTTP-only constructs the actual required HTTP route graph, policy/auth and mandatory persistence, while declining event registrations, gateway connections, generator/agent work, session resume/recovery, SDK prewarm, MCP discovery and resource watchers that can schedule event work. Review whether unrelated passive registration can safely remain and test the decision explicitly; a timer that later produces an event is already a violation. Verify `/health`, required authenticated repair/admin and publication routes plus their failure paths against the real composition. Choose the final route inventory from existing route/verification contracts during review; do not replace production composition with a toy server.

Full mode preserves normal supported startup behavior and intended runtime registrations exactly once, including resource-driven reload. Repeated calls cannot stack gateways, schedules, triggers, generators, recovery loops or watchers. Define startup ordering and which failures prevent event readiness independently of HTTP listen. All failure/status responses remain truthful: valid HTTP readiness does not imply event readiness. Production defaults must not silently switch to HTTP-only.

Narrow or retire `KNOXX_DISABLE_EVENT_RUNTIMES` only once the reviewed lifecycle model is authoritative. Specify its backwards-compatible mapping and banner/timer lifetime, conflicting mode/config behavior and a single source of resolved admission. Preserve disabled-before-stop reset behavior; disabled mutation must not tear down an already owned active runtime or report success. The deprecated trigger-runner facade, admin mutation endpoints, hot reload and background boot must use that same contract rather than competing guards.

## Ownership, ordering and failure laws

Each runtime context owns every timer, watcher, gateway and registration acquired by its operation. Partial start records acquisitions and unwinds only those owned effects; independently running contexts survive. Stop/reset cancel or invalidate owned deferred work and stale promise completions so no stopped runtime is resurrected. Await cleanup as required, report pending/failed cleanup truthfully, and preserve the primary error even if cleanup also rejects. No process-global environment mutation or broad cleanup can affect another verification worker.

Serialize competing lifecycle commands or bind generations/capabilities with a reviewed equivalent. Prove repeated start returns an honest idempotent outcome, start while pending cannot claim completion, stop while starting safely prevents later registration, reset cannot double-register and stale config/completion cannot replace newer state. A reset failure must preserve/describe the real remaining state rather than unconditionally overwrite an `:ok` flag. Rejected or disabled commands produce no new effects. Observing an async failure in a log is insufficient if the response still claims successful operation.

Authenticated `/api/admin/config/events/runtime/start`, `/stop`, `/reset` and any config/resource reload surface use verified actual outcomes, preserving current session guards and `org.events.control`. Distinguish unauthorized/refused/failed/already-running/stopped outcomes and review HTTP status mappings. Do not dispatch work merely to test status or hide failure under HTTP 200. No new admin override may elevate untrusted config into the trusted spawn capability.

## Whole six-outcome proof and red/green sequence

1. Required HTTP routes work through actual HTTP composition with events absent, while mandatory policy/persistence failures still prevent false readiness.
2. Both core startup paths, production bootstrap, hot reload, watcher/debounce and delayed callbacks produce zero prohibited HTTP-only effects. Controlled clock/effect adapters plus actual route/composition functions are required; mere planner snapshots are insufficient.
3. Start/stop/reset/status laws cover idempotence, concurrency, disabled admission, partial acquisition, asynchronous failure, cleanup failures, stop/reset races and paired instance isolation.
4. Decision/result and real authenticated HTTP surfaces all report refused or failed start/reset truthfully; existing disabled reset safety is retained.
5. Full-runtime startup arms intended effects exactly once and preserves current provenance/capability/default/compatibility semantics.
6. Full relevant backend tests/lint/typecheck satisfy owning zero-warning policy, with compile/boundary/human proof required in addition.

Begin with failing portable law tests, then compiled CLJS adapter/real-handler fixtures. Use modern supported async/await. Negative controls include a deliberately injected forbidden deferred callback, a rejected source start after successful trigger acquisition, cleanup failure after primary failure, stale completion after stop/reset, two independent contexts whose shutdown must not cross, and a false-success response regression. A deliberately failing async fixture must produce nonzero in the official guarded runner; no runtime-only console assertion is qualification. Extend existing disable/prewarm/bootstrap/persistence/route tests rather than deleting meaningful regressions.

Discover future `*-test` namespaces with the actual Shadow `test`/`test-ci` selectors, and `*-e2e` through the explicit e2e selector. Future commands: `pnpm -C backend test`, `pnpm -C backend exec shadow-cljs compile test`, `pnpm -C backend lint`, `pnpm -C backend typecheck`, `pnpm -C backend exec shadow-cljs compile server`, `pnpm -C backend boundary:check`, `pnpm -C backend error-boundaries:check`, and actual `test:e2e`/`test:routes:release` for route/composition changes. Add a dual-host pure-law run if the new portable namespace needs an explicit selector; no existing suite is assumed to discover it automatically. Retain full command scopes, test counts and zero warnings. Existing #181/#182 failures are holds, not waived baselines or touched-only passes.

Human verification ships a dedicated script and document, using the publication verification pair as the repository reference. Bind the served SHA/checkout; own all seed data, ports, timers and output; teardown via trap; verify unauthenticated access, refusal/failure/partial failure and expected successful required routes; print meaningful PASS/WARN/FAIL and exit nonzero on required failure. Exercise isolated actual HTTP behavior and intended full-mode adapter composition without claiming mocks prove live gateways/provider behavior. Any live full-runtime check needs reviewed, explicit local prerequisites and ownership; this planning work launches no backend, provider, PM2, browser or shared service. A UI addition would additionally require the repository browser tour.
