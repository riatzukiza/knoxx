# Proposed human verification for generator lifecycle

This guide specifies the future artifact required by Knoxx AGENTS and issue 160. No runnable implementation script or live backend proof exists in this planning change. The existing task `knoxx-generator-runtime-create` remains Ready / 3 points, with its original card bytes and engine history intact. [The design](../design/generator-runtime-lifecycle-planning.md) retains all five original definitions of done and makes the proposed pure/effect placement amendment explicit.

A future `scripts/verify-generator-lifecycle.sh` must verify its actual running checkout/revision first, fail loudly on missing tools/config/auth/runtime identity, and seed/tear down only its dedicated fictional resource directory. It must not restart PM2 or contact an unrelated backend. A live run needs a deliberately selected isolated Knoxx instance with the reviewed generator driver capability; it cannot borrow shared services, real providers, another run's resources or synthetic administrator identity. Script prerequisites must name the accepted launch/config/auth mechanism discovered in implementation; this proposal supplies none of them by assertion.

The walkthrough must show:

1. The source revision, isolated resource root and ownership token match the tested runtime. Before start, the authorized `GET /api/admin/config/events` retains its legacy envelope and yields `runtime.generators.running = false`, with the documented empty/stopped generator descriptor state.
2. A fictional supported generator starts through the actual event-runtime integration; observe its driver acquisition and exact ID in `runtime.generators.generators`. Logging a catalog entry or inspecting `availableGeneratorKinds` does not prove activation.
3. Repeated start preserves the reviewed idempotence outcome. An unsupported/malformed generator and a driver that rejects startup each produce a visible failure, no false active status, and owned-handle cleanup.
4. Stop and repeated stop release only that run's acquired handles and report the reviewed stopped state. A second independent context's resources/status survive the first context's stop/reset; use controlled isolated fixture contexts, never another operator's real run.
5. Exercise the real route's unauthenticated and insufficient-permission denial. Do not bypass its existing session/permission guard to obtain a passing screenshot or response.
6. Preserve the nested `runtime.generators` status-map/inner-vector shape, existing events/triggers/control/option fields, and the separately documented legacy dispatcher running-field meaning. Retain source and fixture identities with every result.
7. Exit nonzero on any failed prerequisite or assertion, including asynchronous failure. Print a truthful outcome summary; use traps to clean only exact owned paths on success, failure and interruption. Do not suppress an in-scope failure as WARN. A missing live prerequisite remains a recorded blocker, never a mocked-live success.

Before live verification, inspect the actual accepted result of the separately owned issue 161 capability work and guard its current source/overlap identity. Offline compatibility fixtures must preserve runtime-owned `:action/capabilities` attachment through config/start/stop/reload and tools-route composition. Attempted capability overrides in fictional generator/resource and HTTP payloads must not replace trusted authority or grant spawn capability. Retain source/schedule/trigger behavior, internal versus external provenance, captured Discord compatibility and disabled/no-spawn controls. Verify with supplied doubles and legitimate constructed trusted contexts; do not invoke a real session, Discord client or provider. This is a compatibility requirement, not adoption or approval of issue 161, and creates no new hard card dependency.

Offline pure, adapter and real-route injection tests precede this walkthrough and can run without a server listener or provider. Their proof is separate from the user-visible API's actual operational observation. No browser tour is claimed for an unchanged API-only surface; if implementation adds UI, the repository's tour requirement applies. Existing lint/architecture holds under issues 181/182 remain visible; no gate, package policy or operational setting changes here.
